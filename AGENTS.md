# Правила работы с проектом

Инструкции действуют для всего репозитория. Прямые указания пользователя имеют приоритет. Общение и отчеты — на русском; именование кода — в существующем стиле проекта.

## О проекте

NBA Randomizer — Android-приложение для NBA 2K: загрузка ростеров и характеристик, генерация команд, замена игроков, поиск, фильтрация, история и прозвища.

- Один модуль `app`, Kotlin, XML, ViewBinding и Fragment. Состояние экранов хранится во ViewModel; для сохраняемых параметров используется SavedStateHandle.
- UI построен на Android Views и Material Components. Переходы используют `com.google.android.material.transition.platform.MaterialContainerTransform` и `android.transition`.
- Текущий минимум — Android 10 / API 29; compileSdk и targetSdk — 35. Актуальные настройки проверять в `app/build.gradle.kts`, версии зависимостей — в `gradle/libs.versions.toml`.
- Две сборки: `debug` с applicationIdSuffix `.debug` и `release` с основным applicationId.

## Структура

Основной пакет: `app/src/main/java/com/example/nbarandomizer/`.

- `ui/` — фрагменты; `ui/components/` — общие компоненты отображения; `ui/providers/` — оформление View.
- `viewModels/` — состояние экранов, загрузок и игровой сессии.
- `adapters/`, `adapters/viewholders/`, `callbacks/` — списки, ViewHolder и сравнение элементов.
- `animators/`, `extensions/` — анимации и общие функции.
- `models/` — игроки, рейтинги, настройки и история; `services/PlayersService.kt` — получение, разбор и кеширование ростеров.
- `app/src/main/res/layout/` — экраны и общие XML-блоки; `app/src/main/res/raw/` — встроенные данные.
- `outputs/` — локальные планы, отчеты и материалы проверок. Папка исключена из Git.

## Границы изменений

- Выполнять согласованный запрос. Дополнительные улучшения, исправления посторонних проблем и изменения поведения сначала обсуждать с пользователем. Уже разрешенные действия повторно не согласовывать.
- Если запрошены только анализ, объяснение или проверка, код не менять.
- При рефакторинге сохранять игровую логику, внешний вид и сценарии взаимодействия. Не смешивать его с функциональными улучшениями.
- Не переписывать пользовательские тексты, сообщения, подсказки и подписи, включая их формулировки и стиль, без отдельного запроса.
- Не менять архитектуру UI, механизм навигации, зависимости, SDK, варианты сборки или подпись как побочный эффект другой задачи.
- `Player.id` соответствует позиции игрока в исходном ростере из 100 игроков. Это принятое устройство проекта; не менять схему ID без согласования. Отличать ID игрока от позиции строки и идентичности места в команде (`TeamSlot`).
- Не перерабатывать PlayersService заодно с UI-задачами.
- Перед работой проверить `git status`, текущую ветку и diff. Продолжать в ветке текущей задачи, сохранять пользовательские изменения, не откатывать их и не перезаписывать.

## Новый код

- При написании нового кода придерживаться принципов SOLID.
- Повторяющиеся XML-элементы выделять в отдельные переиспользуемые компоненты: общие layout с `include` / `merge` или View-компоненты с собственной XML-разметкой. При добавлении нового UI использовать существующие подходящие компоненты.

## Состояние и поведение UI

- При выделении XML сохранять размеры, отступы, constraints, свойства нажатий, стили и форму фотографий. Учитывать `wrap_content`, узкие карточки и разные родительские Layout.

## Анимации

Сохранять существующее разворачивание экрана из исходного элемента и обратное сворачивание. Изменение механизма или параметров анимации требует согласования, если оно не входит в запрос.

Текущие параметры для проверки изменений:

- MaterialContainerTransform: 350 мс, LinearOutSlowInInterpolator, прозрачный scrim, drawingViewId `R.id.container`.
- Замена игрока: 250 / 250 / 150 мс, масштаб 2 → 0.9 → 1, OvershootInterpolator(0.5).
- Размытие: 350 мс, радиус 1 → 25; сохранять проверки доступности API.

Не заменять эти эффекты без обсуждения.

## Сборка и проверки

Использовать Gradle Wrapper. На текущей машине доступен JDK 21; путь ниже локальный, в другой среде его нужно проверить.

Пример полной проверки для изменений логики, состояния или жизненного цикла:

```powershell
$env:JAVA_HOME = 'C:\Users\AsdWELL\.jdks\jbr-21.0.11'
.\gradlew.bat :app:assembleDebug :app:assembleRelease :app:lintDebug :app:lintRelease --console=plain --max-workers=2
git diff --check
```

- Выбирать проверки по характеру изменений. Для правок документации сборка не нужна. Для изменений логики, состояния или жизненного цикла выполнять соответствующую сборку, Lint и проверки затронутых сценариев.
- Для изменений, связанных только с UI, не писать и не запускать автоматические тесты, включая unit-тесты, Robolectric и инструментальные UI-сценарии. Вместо этого собрать debug APK и развернуть его на подключенном Android-смартфоне через ADB. Полная проверка из примера выше для таких изменений не требуется.
- Перед установкой проверить `adb devices -l`. Если подключен один доступный смартфон, использовать `adb install -r app/build/outputs/apk/debug/app-debug.apk`; при нескольких устройствах указать нужный смартфон через `adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk`. Использовать ADB из `platform-tools` Android SDK.
- Если смартфон не подключен либо ADB показывает `offline` / `unauthorized`, сообщить об этом пользователю и предоставить собранный debug APK. Не заменять отсутствие устройства автоматическими тестами для чисто UI-изменений.
- При ошибках инкрементального кеша между дисками C: и D: можно добавить аргументы `'-Pkotlin.incremental=false'` и `'-Pkotlin.compiler.execution.strategy=in-process'`.
- Не оставлять новые тесты в проекте. Необходимые временные проверки создавать вне репозитория и удалять после выполнения. Временные источники и зависимости можно подключать через внешний Gradle init script; файлы зависимостей проекта ради них не менять.
- Существующие авторские тесты сохранять. Не создавать проверки, которые только повторяют реализацию.
- После развертывания UI-изменений указать пользователю, что проверить вручную: затронутые экраны и действия, повторную привязку строк, поворот, смену темы и узкую разметку по мере применимости. Установка APK сама по себе не подтверждает правильность отрисовки и поведения UI.
- Не удалять установленное приложение, его данные или ключи подписи ради установки APK без разрешения пользователя.

Артефакты сборки: `app/build/outputs/apk/debug/app-debug.apk` и `app/build/outputs/apk/release/app-release-unsigned.apk`. Отчеты Lint и тестов находятся в `app/build/reports/`.
